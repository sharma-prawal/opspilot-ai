# OpsPilot AI v0.5.0 — Bring Your Own Incident Data

v0.5.0 lets you investigate your own incidents, not only the synthetic scenarios: upload sanitized logs, metrics,
traces and change events, check what was extracted, and get an evidence-backed RCA from your local model. Analysis
of uploaded files is **read-only**: OpsPilot suggests remediation but never executes it and never claims recovery.
It remains an experimental, local-first POC.

Base: published v0.4.0 (`main` at `e8d5363`). Decisions: D103–D108 in [DECISIONS.md](../DECISIONS.md).

## What is new

### Analyze files (`/incidents/new`)
- Describe the incident (title, description, affected service and other affected services, severity, approximate
  time and timezone), then drag and drop or pick up to 5 files.
- **Preview before storing:** records per signal (logs, metrics, trace spans, change events), rejected rows with
  the reason, services, time range, timezones, redactions, coverage warnings (e.g. incident time outside the data,
  declared service with no records, no metrics) and sample records with their `file:line` source.
- **Create incident & start analysis** stores the upload and starts the investigation; progress, evidence, RCA and
  report appear in the usual investigation view.
- Incidents are labelled **Demo · simulator** or **Uploaded evidence** on the overview, incident list, incident and
  investigation pages.

### Supported files
| File | Read as |
|---|---|
| `.log`, `.txt` | one entry per line starting with a timestamp (ISO-8601, epoch, or web-server `[18/Nov/2026:10:02:03 +0000]`); level and `key=value` pairs recognized; stack-trace lines join the entry above; JSON lines also accepted |
| `.json` | arrays of objects, an object holding one, JSON Lines, or OTLP/JSON traces (`resourceSpans`); each object becomes a log, metric sample, trace span or change event (deployment, rollback, migration, config change, alert) |
| `.csv` | a timestamp column plus one numeric column per metric, `metric,value[,unit]` rows, or an event-type column |

Limits: 5 files, 5 MB each, 8 MB total, 50 000 records per incident.

### Normalization without invention
- Every record keeps its source (`file:line`, `row`, `item` or `span`), original timestamp and how its timezone was
  established (offset as written, epoch, or `assumed <zone>` for timestamps without one), its service and whether
  that came from the record or from the service you declared for the file, and its unit when the file states one.
- Records without a usable timestamp or service are rejected and reported, never filled in. Date-only values are
  rejected. Missing log levels are inferred from keywords and flagged as inferred.

### Real investigation, read-only
- The unchanged LangGraph workflow and your configured model investigate the upload. A file-backed evidence provider
  answers `search_logs`, `query_metrics`, `list_service_metrics`, `list_recent_deployments`, `get_config_changes` and
  `get_service_dependencies` from the stored records; its tool calls are labelled `opspilot-uploaded-evidence`.
  Runbook and past-incident retrieval still uses the RAG knowledge base, so operational evidence and knowledge
  documents stay distinct.
- Live health, runtime configuration, datastore and queue state cannot come from files: those tools report "not
  available" and the gaps appear in the report.
- Uploaded incidents never request approval and never execute anything. The model's plan is checked by the same
  evidence gates and kept as **suggested remediation**. Outcomes are `analysis_complete` or `analysis_inconclusive`;
  the incident stays open.
- The report adds "Suggested remediation (not executed)" and "Recommended next investigation steps", and cites the
  uploaded file and line for each piece of evidence. **Download Markdown** saves it.

### Privacy and deletion
- **Sanitize files before uploading.** Credential-like values (password/token/secret/API-key fields, bearer and
  basic credentials, AWS keys, private keys) are redacted at parse time as a safety net; other sensitive data is not
  detected.
- Raw files are kept only under `UPLOAD_DIR` (default `var/uploads`, git-ignored, files 0600 in 0700 directories),
  normalized records only in the local database (not readable by the MCP database roles). Inference is local.
- File content is untrusted data, never instructions; the browser sends it as JSON through the existing BFF
  (operator-only, CSRF-checked, 12 MB body cap). Validation errors no longer echo the rejected request body.
- **Delete uploaded data** (incident page) removes the files, normalized records, investigations, evidence, tool
  calls, events and LangGraph checkpoints of that incident only. `make uploads-purge` (API stopped) removes uploads
  older than `UPLOAD_RETENTION_DAYS` (default 14); `uv run opspilot uploads list` lists them.

### Example data
Synthetic files for a checkout outage after a payment-service deployment, in
`apps/web/public/examples/uploads/`: `checkout-api.log`, `service-metrics.csv`, `change-events.json` and
`checkout-traces.json` (with an unrelated earlier deployment and one fake credential that must be redacted).
Download them from the upload page or use **Load example into the form**; regenerate with
`scripts/generate_upload_examples.py`.

### Other changes
- Incident references come from a durable per-day counter (migration `0010`): concurrency-safe, never reused after
  a deletion.
- Migrations `0009` (incident `evidence_source`, `ops.uploaded_datasets`) and `0010`; run `make migrate`.
- `scripts/e2e-api.sh` accepts `E2E_LLM_MODEL` (process-level model override) and uses a separate e2e upload
  directory.

## Verification (development testing)

- Tests for parsing (formats, malformed and empty files, missing timestamps/services, redaction, unsafe names),
  the provider and graph (cited read-only analysis, uncertain result with next steps, refusal to approve or
  execute), the API (preview, validation, investigation without action requests, deletion scope, credential-free
  errors, reference allocation under concurrency and after deletion), the BFF and the web helpers.
- Live runs with the synthetic example upload (see PROGRESS.md for details): with `qwen3:8b` through the UI, and
  with `qwen3.5:9b-q4_K_M` in the Playwright upload test (`e2e/upload.spec.ts`: files from disk via
  `setInputFiles`, preview, investigation, cited report, Markdown download, deletion).

## Limitations

- Parsers cover common shapes, not every format (e.g. syslog lines without a year are rejected; Prometheus range
  JSON is not read). Check the preview.
- Conclusions depend on what you upload; without metrics, impact stays unknown and the result is usually
  inconclusive. One synthetic example scenario was used for development; this is not an evaluation of RCA accuracy
  on real incidents.
- Hypothesis confidence is the model's own estimate, not a calibrated probability, and is labelled so in the UI and
  the Markdown report. In the qwen3.5 upload run the top hypothesis was rated 100%: that means the model saw no
  competing explanation in the uploaded evidence, not that the cause is statistically established.
- Redaction is a safety net, not a data-loss-prevention tool.
- The official evaluation (`docs/evaluation/BASELINE.md`) still reports the v0.2.1 simulator run; the simulator path
  is unchanged.

## Upgrade notes

Run `make migrate`. Optional `.env` keys: `UPLOAD_DIR`, `UPLOAD_RETENTION_DAYS` (see `.env.example`). Existing
incidents are simulator incidents and behave as before.
