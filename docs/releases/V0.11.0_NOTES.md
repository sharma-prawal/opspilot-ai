# OpsPilot AI v0.11.0 — AWS CloudWatch Logs & Metrics (DRAFT — not yet released)

> **Status: Draft / not yet released.** Implemented on `feature/aws-cloudwatch-v0.11.0` from v0.10.0
> (`2154211`). Not pushed, merged, tagged or published. **Verified only against a synthetic CloudWatch protocol
> fixture driven by the real AWS SDK — no real AWS account, credential, region endpoint or log group has been used.**

AWS CloudWatch joins Loki, Prometheus, Datadog and Azure Monitor as an optional, backend-configured, strictly read-only
evidence provider. It feeds the existing snapshot-driven LangGraph investigation; there is no AWS-specific agent,
graph or RCA pipeline, and no AWS write or remediation capability anywhere.

## Implemented and fixture-tested

- **Connector** (`opspilot_shared/connectors/cloudwatch.py`, `cloudwatch_resources.py`; D137–D142) through boto3/botocore:
  - Logs Insights QL: six built-in templates (errors, warning/error chronology, timeouts/dependency failures,
    start-up/version/configuration indicators, correlated failures, log-based error count); `StartQuery` →
    bounded `GetQueryResults` polling (≤ 3 in flight, ≤ 40 polls or 60 s) → `StopQuery` only for the collection's own
    unfinished query (shielded, also on cancellation); partial rows kept and marked; scan statistics recorded.
  - `GetMetricData`: ALB target 5xx / request count / target response time p95 / unhealthy targets, ECS CPU/memory,
    Lambda errors / invocations / duration p95 / throttles, up to 10 configured custom metrics per service; one statistic
    per template, retention-aware periods, ≤ 3 pages, AWS-documented units, absent periods never filled.
  - Explicit service → log group / dimension mapping (`CLOUDWATCH_RESOURCES_FILE`), which is the allowlist; unmapped
    resources are recorded as *not queried* and never sent; bounded discovery of mapped services only.
  - Authentication by explicit mode: named profile (SSO-capable; never logs in), workload role, or explicit (preferably
    temporary) keys; optional assumed read-only role and expected-account check; no silent fallback; lazy clients.
  - Commercial-partition region validation; endpoint overrides ignored; regional endpoints verified per client.
  - Connection test: account (STS), configured log-group existence, one 1-minute Logs Insights probe per group, one
    metric probe — per-log-group *readable / access denied / not found*.
- **Pipeline:** provenance gains `aws` (region, account, log groups, query ID/status/polls/statistics, stop result, or
  metric definitions, period, status codes); the prompt note, report banner, provenance table, *Evidence coverage*
  ("not queried (no mapped CloudWatch resource)", "only the approved log groups and mapped resources were searched")
  and next steps (CloudTrail, AWS Config) name CloudWatch. No database migration.
- **RCA truthfulness (D143), all read-only RCAs:** deterministic notes for version numbers or quoted identifiers that
  appear nowhere in the collected evidence, and for deployment/configuration-change claims that cite no observed change
  line. Found in the real-model run; the model's text is never edited. Simulator RCAs are not annotated.
- **Web (Visual Experience 2.0 kept):** CloudWatch in the Integrations catalogue (now *implemented*), capability matrix,
  connector panel (region, profile/role, account after a test, log groups, IAM actions), connected intake (region and
  account line, per-log-group badges, cost note, fixture demo incident, query provenance with log groups and query ID),
  incident provenance; BFF allows `connectors/cloudwatch/(test|services)`, operator-only.
- **Security:** `CLOUDWATCH_*` and `AWS_*` are denied to the Next.js process; keys never appear in API responses,
  snapshots, reports or logs; AWS error text (which can name SSO session e-mails) is not passed through.
- **Fixture and tests:** `scripts/cloudwatch_fixture.py` (Logs JSON 1.1, CloudWatch JSON 1.0, STS query/XML; SigV4
  required) with a fictional api-gateway → checkout-service → inventory-service incident and failure scenarios;
  `make cloudwatch-fixture`; botocore `Stubber` unit tests; investigation, API and Playwright journeys.

## Not verified / limitations

- **No live AWS verification**: authentication against AWS, IAM resource scoping (the example policy follows the
  Service Authorization Reference), Logs Insights syntax acceptance of the templates, quotas and scan costs.
- One region and account per API process; no cross-account observability, GovCloud, China or ISO partitions.
- Logs Insights QL only; built-in templates only; keyword regular expressions are English.
- No CloudTrail/AWS Config change history, X-Ray traces, alarms, live state or console deep links.
- The connection test runs small, billed Logs Insights queries; `StopQuery` permission cannot be probed.
- The claim checks are pattern-based heuristics: unrecognized phrasings are not flagged.

## Upgrade notes

- New dependency: `boto3` (and botocore). Loaded only when `CLOUDWATCH_ENABLED=true`.
- New settings (all optional, off by default): see `.env.example` → *AWS CloudWatch*.
- No migration; existing data, uploads and other connectors are unchanged.
