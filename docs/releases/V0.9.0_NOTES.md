# OpsPilot AI v0.9.0 — Datadog Observability Integration

Approved release of `feature/datadog-v0.9.0` at `d2957762e3e2b26c90e1147c1c19dc2af49f0523`, merged into `main` on top
of v0.8.0 with a non-rewriting merge commit.

## At a glance

- **Implemented:** Datadog logs, metrics (APM trace metrics through the timeseries query), service discovery and APM
  span search.
- **How it was tested:** against a **synthetic Datadog API fixture** that follows Datadog's documented request and
  response structures.
- **No real Datadog organization has been used for validation.** Live verification is outstanding; the procedure is
  in [DATADOG.md](../integrations/DATADOG.md#optional-live-verification).
- **Deployment and change event collection is deferred.** Change history from Datadog stays *unknown* and is never
  presented as "no change".
- **Known limitations:**
  - Only indexed spans are searchable, so traces can be partial.
  - APM metric templates are operation-specific: the built-ins assume `trace.http.request`; other integrations need
    their own templates.
- **Read-only:** Datadog investigations never approve, execute, or claim verified recovery. OpsPilot never writes
  to Datadog.
- **Reports:** connected-source reports (Datadog, Loki, Prometheus) now include **observed change indicators** from
  logs and an **Evidence coverage** table (observed / contradicting / searched, nothing found / not collected).
  Observed version and start-up lines are indicators of a possible change, not a verified deployment history and
  not proof of cause.

Datadog becomes an optional, read-only **evidence provider**. OpsPilot can collect logs, APM trace metrics and
indexed APM spans for one service and one bounded window from a configured Datadog organization. It previews them and
freezes them as the incident's snapshot. The existing LangGraph workflow then investigates the snapshot: no
Datadog-specific agent, no new tables, no migration.

**Verification status:** tested against a synthetic contract fixture built on Datadog's documented request and
response structures. **Not verified against a live Datadog organization.**

## What's new

- **Datadog connector**, off by default. Set `DATADOG_ENABLED`, `DATADOG_SITE`, `DATADOG_API_KEY` and
  `DATADOG_APP_KEY`, and optionally `DATADOG_ENV`, `DATADOG_LOG_INDEXES` and `DATADOG_MAX_SPANS`:
  - **Logs** via `POST /api/v2/logs/events/search`, cursor-paginated with hard limits;
  - **Metrics** via `POST /api/v2/query/timeseries` (named queries and formula): 5xx ratio, trace error ratio, p95
    latency, request rate, and optional host CPU;
  - **APM spans** via `POST /api/v2/spans/events/search`: error spans plus the other indexed spans of up to 10 of
    their traces;
  - **Service discovery** via a single bounded log aggregate over the `service` facet;
  - **Connection test**: API-key validation, then a per-product probe that reports readable, permission missing,
    not available, rate-limited or unavailable.
- **Truthful normalization:**
  - Datadog `null` intervals are left out, never filled in.
  - A span is `error` only when Datadog flags it, otherwise `unset`.
  - Spans whose parent was not indexed mark their trace as partial.
  - Dependencies come only from returned parent/child spans.
  - Change events are not collected; change history stays unknown.
- **Provenance:** `datadog/<template>/<service>:entry|point|span N` citations. Each query records its signal, site,
  pages and Log Explorer link. The report's provenance table adds the site and signal.
- **UI (Visual Experience 2.0 kept):**
  - Datadog in the provider selector and the Integrations catalogue, with per-signal template groups and per-signal
    test results;
  - a span preview tab, and charts of the metric points as returned (gaps drawn as breaks);
  - **Open in Datadog** links for log queries;
  - a *synthetic fixture* label and a fixture demo incident.
- **Synthetic fixture:** `make datadog-fixture` serves a fictional Datadog API on 127.0.0.1. The incident:
  orders-api → inventory-service → inventory-db lock contention. It also covers partial traces, a missing series,
  null gaps, untagged logs and the failure modes. `E2E_DATADOG=1 make e2e` runs the browser journey against it.

## Evidence-state handling

- **No "nothing changed" from missing data.**
  - Connected investigations now collect version, start-up and configuration log lines as change observations;
    they were invisible to the WARN+ search.
  - The evidence digest names those observed events when change history is unknown.
  - A deterministic check flags any hypothesis or summary that claims no change occurred while change history was
    not collected.
  - The report adds an *Evidence coverage* table: observed, contradicting, searched-none-found, not collected.
    Observed lines are labelled as indicators: not a verified deployment history and not proof of cause.
  - Real-model result on the fixture (local `qwen3.5:9b-q4_K_M`; development testing, not an evaluation):
    - before: "No internal deployment or configuration change caused the fault" (85%);
    - after (two runs): the top hypothesis is the observed inventory-service 3.8.0 deployment, with no negative
      change claim.
- **Service names** may contain `.` and `_` (e.g. `billing.worker_v2`) for Datadog. Values are validated and every
  character Datadog's search syntax documents as special is escaped. Names are kept exactly, never rewritten.
  Loki/Prometheus still accept slugs only.
- **Span search** templates are service-scoped and need no operation name. Only APM metric templates depend on
  `trace.http.request`, because Datadog names trace metrics per operation.

## Security

- Destinations come from a fixed site allowlist: requests go only to `https://api.<site>`. The loopback-only
  `DATADOG_LOCAL_API_URL` exists for the fixture.
- `ReadOnlyHttp` gains `post_json`, limited to a per-connector POST allowlist. Datadog's allowlist is four documented
  read-query endpoints. Loki and Prometheus still cannot POST, and no PUT/PATCH/DELETE method exists.
- Requests accept template IDs only, never a query, URL, host, path, site or method.
- Limits:
  - a window of at most 6 h;
  - at most 1000 records per page and 5 pages per query, plus the line, span and series limits;
  - at most 2 Datadog requests in flight;
  - on a 429, at most 2 retries, and only when the reset is 10 s or less.
- Keys are backend-only (`DATADOG_` and `DD_` are excluded from the web process). They never appear in responses,
  snapshots or reports, and are scrubbed from errors.
- Datadog incidents are read-only end to end: no approval, no execution, no verified-recovery claim, and no Datadog
  tool for LangGraph or MCP.

## Compatibility

- No migration, schema or model change. Simulator safety policy and approval logic are unchanged.
- Loki/Prometheus snapshots keep their v0.6 prompt note and report banner wording (tested). Like every connected
  snapshot, they now also collect change observations from logs, list them in the digest when change history is
  unknown, and add the *Evidence coverage* report section. Their provenance gains a `signal` field.
- API: the connector list includes `datadog` (configured or not) and removes it from `planned`. `ConnectionStatus`
  adds `partial`, `rate_limited` and `signals`. `services` adds `notes`. Preview adds `series` and `collected.span`.
  Up to 3 sources are accepted.

## Known limitations

- Not verified against a live Datadog organization.
- Datadog Events and Change Tracking are deferred.
- Only indexed spans are searched, so traces may be partial.
- Service names with `:`, `/` or upper case are not queried.
- The built-in APM templates assume `trace.http.request`.
- Explorer links exist for logs only.
- API key + application key auth only; personal or service access tokens are not supported.
