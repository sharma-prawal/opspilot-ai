# OpsPilot AI v0.2.1 — Phase C0 hardening

v0.2.1 is a hardening release on top of v0.2.0 (`9ec857c`). It fixes the findings of an independent Codex audit
of v0.2.0 (4 High, 8 Medium and 1 Low verified finding, plus 3 suspected risks). It also fixes the defects found by
three further rounds of independent verification of that work (C0-F1…F5, C0-G1…G4, C0-H1/H2). It adds no new
incident scenarios or product features.

**Release status: experimental, local-first.** The final independent verification
([`PHASE_C0_H_INDEPENDENT_VERIFICATION.md`](../audits/PHASE_C0_H_INDEPENDENT_VERIFICATION.md)) gave a
**CONDITIONAL** sign-off. The earlier release blockers are verified closed, and no new release blocker was found
on the supported ingestion, investigation, approval, cancellation or takeover paths. The sign-off depends on the
claims staying within the scope described below; see [Known limitations](#known-limitations).

Evidence for every item (reproduction, root cause, change, tests, remaining risk):
[C0](../audits/PHASE_C0_REMEDIATION.md) · [C0-F](../audits/PHASE_C0_F_REMEDIATION.md) ·
[C0-G](../audits/PHASE_C0_G_REMEDIATION.md) · [C0-H](../audits/PHASE_C0_H_REMEDIATION.md). Each independent audit is
preserved verbatim in [`docs/audits/`](../audits/).

## Deployment restriction: one execution owner per database

v0.2.1 supports **exactly one execution owner per database** and enforces this at runtime. Every API process, CLI
demo and evaluation run first takes a PostgreSQL advisory lock. A second one fails at start-up with
`execution_owner_unavailable`. `make dev` starts one worker; `--workers N>1` and `WEB_CONCURRENCY>1` are refused.
Stop the dev API before `make evaluate` or the CLI demo. Python tests and `make e2e` share the test database and
cannot run at the same time. Multi-worker operation is **not supported**.

## Incident recovery verification

- **Impact is `ongoing`, `recovered` or `unknown`.** Missing, failed or insufficient telemetry can no longer
  resolve an incident. `unknown` blocks remediation and escalates.
- **Recovery needs complete, affirmative evidence.** Recovery counts only when there is positive, fresh
  post-action health for:
  - the alerting service;
  - every action target;
  - every service known to have been unhealthy, whatever its initial health (unknown included).

  The scope comes from the observed incident, not from the model's citations, and every excluded anomaly is listed
  with a reason. Metric-specific residual limits mean "improved" is never reported as "recovered". Any condition
  not checked within the budget produces `verification_incomplete`. The outcome re-derives the required conditions
  before it reports `mitigated`.
- **Uncertain diagnoses are not proposed for approval.** A plan is withheld when any of these holds:
  - confidence is low;
  - escalation was requested;
  - the top hypotheses compete with disjoint evidence;
  - the investigation budget ran out.

## Durable and cancellation-safe workflow transitions

- **Approval decisions survive crashes.** Decisions go through a transactional outbox with at-least-once
  delivery, idempotent effects and start-up reconciliation. Graceful shutdown leaves runs resumable
  (`interrupted`), not `cancelled`.
- **Terminal states are final.** Investigation status changes go through one locked compare-and-set against a
  transition policy. A database trigger also keeps `completed` and `cancelled` absorbing. Only an explicit
  operator resume reopens `failed`. Reconciliation, outbox delivery, expiry and restarts cannot move a cancelled
  investigation back to `awaiting_approval`.
- **Cancellation cannot race execution.** The action server claims an approved action under a row lock before
  any effect. Cancellation revokes unclaimed approvals and undelivered decisions in the same transaction. Once
  execution has been claimed, cancellation is refused.

## PostgreSQL-backed admission and execution ownership

- **One active investigation per incident**, enforced by a partial unique index, plus a database execution lease
  per workflow.
- **Atomic, bounded admission.** An admission slot is reserved before anything is written, so excess starts get
  HTTP 429 with nothing persisted, even when they arrive concurrently. Accepted work whose dispatch failed is
  re-dispatched by the maintenance sweep.
- **Bounded resources.** Embedding and chat requests to the local model are concurrency-bounded per process.

## Ownership epochs and checkpoint fencing

- **Explicit runtime lifecycle:** `INITIALIZING → ACQUIRING_OWNERSHIP → READY → OWNERSHIP_LOST → STOPPING →
  STOPPED`.
  - Only `READY` admits or runs work, reconciles, delivers decisions or runs maintenance.
  - `READY` is entered only after initialization and an affirmative database fence check. If ownership is lost
    before that, start-up fails.
  - Losing ownership is synchronous and sticky: execution stops at once and the served API exits.
- **Epoch fencing in the database (migration 0008).** Each new owner increments an epoch.
  `ops.execution_fence(epoch, pid)` checks that the epoch is current and that the owner's lock session is still
  alive. These writes call it:
  - every LangGraph checkpoint write, through a statement trigger on the checkpoint tables;
  - runner lease and persistence transactions;
  - reconciliation writes;
  - the action server's execution claim. Approval tokens carry the minting owner's epoch, and unbound tokens are
    refused.

  The fence holds a shared lock on the epoch row until the writing transaction ends. A takeover therefore waits for
  in-flight fenced writes, and the stale owner's later writes are refused.
- **Scope of this guarantee.** The fence covers normal application writes and the unprivileged MCP database
  roles. It does **not** protect against the holder of the application's database-owner credential
  (`opspilot_app`), which owns these tables and could disable the triggers. Operator control-plane writes (start,
  cancel, decide) are not fenced. A process that has just lost ownership can still commit them. Independent
  verification reproduced this as a recoverable delay (resolved by lease or outbox recovery), with no stale
  execution.

## Atomic document revision consistency

- **Serialized publication (migration 0007).** Ingestion publishes each document revision in one transaction
  under a per-document advisory lock. It assigns `committed version + 1` from the row it read under that lock.
- **Database constraints on the document row.** A content-hash change must increase the version, and the version
  never decreases. A deferred foreign key keeps every committed chunk on its document's current version.
- **Pinned retrieval.** Each returned passage is pinned to its document's `(version, content hash)`. Expansion and
  the final revalidation require that exact committed revision and fail closed (with a warning) on any change. One
  document never appears with two revisions in a response.
- **Scope of this guarantee.** Revision identity is *logical source-content* identity. Physical chunk IDs are
  **not** immutable: re-indexing unchanged text with different chunk settings can reuse a chunk ID and version for
  a different slice of the same source. A direct chunk `UPDATE` by the trusted database owner is not blocked
  either. Neither happens through the supported ingestion or tool paths, and the MCP roles cannot write to the
  knowledge base.

## Lifecycle-aware RAG and historical citation integrity

- Document lifecycle (status, version) is tracked without re-embedding.
- Current guidance outranks unreviewed and superseded material *before* top-k truncation.
- **No superseded guidance in investigations.** The agent's knowledge tools exclude superseded or withdrawn
  documents. Every returned passage is revalidated against the committed lifecycle, including between ranking and
  section expansion. Historical search stays available through the authenticated operator API.
- **Current-runbook section coverage.** The agent receives up to four further sections (diagnostics, remediation,
  constraints) of the top-ranked current runbook, not just the fragment that ranked.
- **Citations are self-contained snapshots.** Each citation stores the full passage, its SHA-256, the document
  version, lifecycle status and retrieval time. An RCA remains verifiable after its sources are re-ingested.
  Earlier full document revisions are not archived: the snapshot is the historical record.
- Retrieval degradation (keyword-only fallback) is reported through MCP to the agent.

## Approval security, token redaction and least-privilege MCP access

- **Authenticated operator UI.** Sign-in issues a signed, HttpOnly, SameSite=Strict session. Mutations require
  same-origin, a session-bound CSRF token, JSON and the operator role. Decision identity comes from the session,
  and missing configuration fails closed.
- **Every backend mutation requires the operator token**, so callers cannot bypass the BFF.
- **Action-bound approvals.** Each approval is bound to the action ID and the parameter hash, is HMAC-signed and
  expires; the executor verifies it again. Execution is idempotent.
- **No credentials in records.** A central redaction policy covers tool-call history, workflow events, API
  responses, structured logs and the BFF relay. Spent approval tokens are cleared from workflow state.
  `opspilot sanitize-secrets` (dry run by default) finds records written by earlier versions.
- **Least-privilege MCP servers.** Each server process gets a minimal environment: no `.env`, operator token or
  web secrets. Each has its own database role: the read role reads (and records retrieval traces); the action
  role writes only sandbox state and an action request's status, and may call the fence. Neither MCP role can change the ownership epoch, disable the checkpoint triggers or assume the
  application role (verified independently by connecting as each role).
- Agent tools still accept no free-form shell, SQL or file paths.

## Evaluation

The official evaluation ran at `2116ef1` (code identical to this release; later commits are documentation only):
`qwen3:8b`, temperature 0, 13 live runs over six scenarios. That is two approve-every-step trials per scenario plus
one INC-001 rejection trial. Results come from [`BASELINE.md`](../evaluation/BASELINE.md), generated by
`make evaluate` and frozen in `datasets/evaluation/history/phase-c0h-2116ef1/`.

**Final system outcomes**: what the gated system did.

| Measure | Result |
|---|---|
| Correct final outcome | **13/13** (6 mitigations, 6 correct non-remediation outcomes, 1 rejection) |
| Executed plan acceptable | 13/13 |
| Recovery verified (`VERIFIED`) | 6/6 |
| Unsafe / forbidden / unauthorised executions | 0 / 0 / 0 |
| Approval bypasses | 0 |
| False-positive remediation rate (negative scenarios) | 0 |
| Citation validity | 1.0 (112 citation snapshot hashes independently re-verified) |
| Mean / max time per run | 37.4 s / 47.9 s |

**Model reasoning**: what the model proposed before the deterministic gates.

| Measure | Result |
|---|---|
| Model's own plan acceptable | **3/12** approve trials (partial pattern conformance) |
| Correct root cause | 7/9 determinable cases (NEG-002 wrong in both trials) |
| Policy interventions | 11, including 1 unsafe proposal blocked |
| Negative scenarios where the model still proposed a rollback | all 6 runs (none executed) |

The correct outcomes come from the deterministic safety policies and human approval, not from the model's
planning.

**Retrieval** (held-out set, 30 questions): hybrid Recall@5 0.972, nDCG@10 0.810. On the agent's own path a
relevant passage reached the RCA prompt for every held-out question (MRR 0.603), with 0 non-current passages.

## Evaluation corrections

- Plan scoring checks order, undeclared extra actions, attempted (including failed) actions and forbidden attempts
  independently, and it is occurrence-aware. A forbidden action can no longer score as an acceptable plan.
- The model's own plan, root cause, verified recovery and policy interventions are reported separately from the
  executed system plan.
- A new agent-path retrieval benchmark and a resource-measurement suite were added. INC-003's answer key is
  checked against a deterministic specification.
- Earlier evaluation artifacts are preserved under `datasets/evaluation/history/`.

## Upgrade notes

1. **Stop the API first.** The 0008 checkpoint trigger refuses writes from a pre-0008 API.
2. Add `OPSPILOT_WEB_SESSION_SECRET`, `OPSPILOT_WEB_OPERATOR_PASSPHRASE`, `MCP_READ_DB_PASSWORD` and
   `MCP_ACTIONS_DB_PASSWORD` to `.env`. `scripts/bootstrap.sh` adds any that are missing.
3. Run `make migrate`. This applies migrations 0004–0008 (all additive) and installs the checkpoint-write
   triggers. Some migrations refuse to run and change nothing:
   - 0005 refuses if an incident already has two active investigations;
   - 0007 refuses if chunks do not match their document's version (re-ingest first).
4. Run `make db-roles` to create or refresh the MCP roles and the fence grant.
5. Run `make stop && make dev` to restart, then sign in at `/login`. Run one API worker per database.
6. Optional: `uv run opspilot sanitize-secrets` (dry run) finds approval tokens stored by earlier versions.
   `--apply` redacts them in place; back up first.

## Known limitations

1. **Experimental, local-first deployment only.** OpsPilot runs on one machine with local models, a sandboxed
   simulator and services bound to `127.0.0.1`.
2. **No production infrastructure access** is implemented or certified. All remediation actions act on the
   deterministic simulator.
3. **One execution owner per database.** Multi-worker or multi-instance operation is unsupported (enforced at
   runtime). Admission and resource bounds are per process.
4. **The database-owner credential is trusted.** Ownership fencing and the revision constraints protect against
   stale normal application writes and the unprivileged MCP roles. They do not protect against the
   `opspilot_app` owner role, which can disable the triggers or edit the epoch.
5. **Physical chunk-ID immutability is not guaranteed.** Revision identity is logical source content. Re-indexing
   unchanged text with different chunk settings can map a chunk ID to a different slice, and direct chunk SQL by
   the owner is not blocked. Citation snapshots remain self-verifying.
6. **No independently sealed, unseen incident evaluation yet.** One author wrote the scenarios, labels and the
   safety gates, and the gates were designed after observing failures on these scenarios. Temperature-0 trials
   measure stability, not generalisation.
7. **Raw model planning is unreliable.** The model's own plans are acceptable in 3 of 12 runs. It misattributes
   the cause in NEG-002 and proposes a rollback in every negative scenario. Deterministic safety policies and
   human approval enforce the remediation boundary. The raw-plan metric is partial pattern conformance.
8. **Historical local development token records need separate sanitization.** Approval tokens (expired) written
   to a local development database by earlier versions remain until the operator runs
   `opspilot sanitize-secrets --apply`. LangGraph checkpoint history also keeps past steps' short-lived,
   action-bound tokens. None are in this repository.
9. **Not ready for multi-user or network-exposed production use.** There is one shared passphrase per role, not
   per-user identity, and backend GET endpoints are unauthenticated on localhost. The MCP servers share an OS
   user, so their database roles do not limit file access.

Other recorded limitations:
- Operator control-plane requests from a process that has just lost ownership can be delayed until lease or outbox
  recovery.
- Recovery residual limits are conservative defaults, not SLOs.
- Terminal rows and checkpoints accumulate.
