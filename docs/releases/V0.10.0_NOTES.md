# OpsPilot AI v0.10.0 — Azure Monitor & Application Insights

Approved release of `feature/azure-monitor-v0.10.0` at `f31fcf15d57c0cf2472b23b66b4540c2c3f2e3de`, merged into `main`
on top of `1c30e88` with a non-rewriting merge commit. It also ships the worktree-independent upload storage fix
(D127) merged to `main` after v0.9.0.

## At a glance

- **New:** Azure Monitor / Application Insights as an optional, **read-only evidence provider** over one Log
  Analytics workspace: traces, exceptions, requests, dependency calls and KQL-derived metrics feed the existing
  snapshot-based LangGraph investigation.
- **How it was tested:** against a **synthetic Log Analytics Query API fixture** (`scripts/azure_monitor_fixture.py`)
  that follows the documented request and response shapes.
- **No real Azure tenant, subscription or Log Analytics workspace has been used for validation.** Authentication,
  API compatibility and queries against a real workspace are not live-verified. The procedure is in
  [AZURE_MONITOR.md](../integrations/AZURE_MONITOR.md#optional-real-azure-verification).
- **Read-only:** OpsPilot never writes to Azure. Azure investigations never approve, execute, or claim recovery.
- **No migration**, no schema, model, safety-policy or approval change.
- **RCAs remain model-written.** The new deterministic claim warnings are heuristic safeguards, not proof of
  diagnostic accuracy (see [About the generated RCA](#about-the-generated-rca)).
- **All read-only reports:** the report-reading guide and claim-calibration warnings also apply to uploaded-file and
  Loki/Prometheus/Datadog investigations, not only Azure.

## What's new

- **Azure Monitor connector** (`opspilot_shared/connectors/azure_monitor.py`), off unless `AZURE_MONITOR_ENABLED=true`:
  - one destination: `POST https://api.loganalytics.azure.com/v1/workspaces/<AZURE_MONITOR_WORKSPACE_ID>/query`
    (public cloud), with the workspace ID validated as a GUID;
  - authentication through the official `azure-identity` credentials, selected explicitly by
    `AZURE_MONITOR_AUTH_MODE` (`service_principal`, `managed_identity`, `azure_cli` for development); no credential
    chain, no interactive sign-in; tokens cached, refreshed before expiry and once after a 401;
  - 13 approved KQL templates: warning/error traces, lifecycle (start-up, version, configuration) traces, exceptions
    with bounded stacks, all traces (off by default), failed requests with up to 10 expanded operations, failed
    dependencies, slowest requests (off by default) and six KQL-derived metrics;
  - connection test: token, a `print` probe, then one `take 1` per table, reported overall, per signal and per table
    (`present`, `not in workspace`, `access denied`, …);
  - discovery: one fixed count by `AppRoleName` (top 50) with notes for records without a role, mixed-case roles and
    names that cannot be service names.
- **UI (Visual Experience 2.0 kept):** Azure Monitor in the connected intake and the Integrations catalogue (per-signal
  and per-table test results, *synthetic fixture* label, Azure fixture demo incident), request/dependency preview with
  sampling and partial-operation markers, provenance with workspace and source tables, report banner and next steps.
- **Synthetic fixture:** `make azure-fixture` (127.0.0.1:8128). Fictional story: payment-service 2.14.0 starts with
  `db.pool.max_size=5`, its SQL calls to orders-db wait for connections, `POST /payments` fails with 503 and orders-api
  answers 502; 2.13.4 with `max_size=50` ends it. orders-api is sampled (`ItemCount` 2), some correlation is
  incomplete, and no deployment record exists. Extra workspaces cover a missing table, `PartialError`, a malformed
  body, 403, 429, 504, 503, 204 and a redirect.

## Evidence handling

- **Partial results** (`PartialError`) keep their rows but mark the query truncated with the error; HTTP 204 is
  *empty* with a note; a missing table is *unsupported* and listed under *Not collected / unavailable*. None of them is
  reported as complete evidence.
- **Sampling.** Metrics are `ItemCount`-weighted estimates. Queries whose records carry `ItemCount > 1` are flagged
  too, and the report's *Evidence coverage* adds an *Incomplete or sampled* row ("record counts understate event
  counts"). Records are never multiplied or invented (D132).
- **Partial operations.** Records whose parent was not returned are `parent_missing`; nothing is reconstructed, and
  an absent dependency record is not evidence that a call did not happen.
- **Dependency targets** (databases, external APIs) are recorded names, never observed services or dependency edges.
- **Change history is unknown.** Start-up, version and configuration lines are log indicators of a possible change,
  not a verified deployment history and not proof of cause; claims that nothing changed are flagged (D125).
- **Capped log searches are not presented as onsets** (uploads and connected snapshots). When the agent's WARN+ log
  search returns only the most recent 300 matches, evidence says "earliest returned … earlier occurrences may exist"
  and the timeline says "earliest returned error" instead of "first error" (D134). Found in the real-model run below;
  simulator wording is unchanged.
- **Model confidence** in reports is the model's own uncalibrated estimate.
- **Claim calibration (D135).** Uploaded and connected reports open with *How to read this report*: observed facts
  (timeline, evidence with source references), evidence-supported hypotheses (summary, ranked hypotheses), verified
  causal conclusions (none: a read-only analysis cannot verify a cause) and unknowns (*Evidence coverage*). The model's
  summary and hypotheses are shown unchanged, followed by deterministic notes when they state a cause as established,
  call an observed start-up or configuration log line a deployment or configuration change, or describe the incident
  as "ongoing". The impact line reads "Impact at the end of the collected snapshot window (…)" and says it is not the
  live state. A suggested `restart_service` carries a visible limitation when the leading hypothesis is a configuration
  problem: a restart reloads the persisted configuration and does not correct it. The workbench shows the same notes.
  Simulator reports and prompts are unchanged.
- **Empty Azure results (D136).** An empty Azure query is *No accessible matching records — access/coverage not
  independently verified* (restricted tables return zero rows without data access), in provenance, preview, the
  coverage table and the provenance table; never "nothing found". 401/403 and `PartialError` handling is unchanged.

## About the generated RCA

- The summary and the ranked hypotheses are **written by the local model**. OpsPilot validates citations against the
  collected evidence, but it does not verify a cause: a read-only analysis has no way to test one.
- The claim-calibration warnings (D135) are **deterministic heuristics** over English wording. They flag a cause
  stated as established, a log line presented as a deployment or configuration change, "ongoing" read as live state,
  and a restart suggested for a persisted configuration problem. They add notes and never edit the model's text.
  They can miss phrasings they do not recognize, and they say nothing about whether the reasoning is right. A report
  without warnings is not a verified diagnosis.
- Confidence values are the model's own, uncalibrated estimates.
- The *How to read this report* guide, the snapshot-anchored impact line and the warnings apply to **every uploaded or
  connected investigation** (uploaded files, Loki/Prometheus, Datadog and Azure Monitor). Simulator investigations
  are unchanged.

## Security

- Fixed public-cloud destination; one allowlisted POST path; no GET; no Azure Resource Manager, metrics, alert,
  automation or ingestion API. The loopback-only `AZURE_MONITOR_LOCAL_API_URL` works only with the `fixture` auth mode.
- Requests carry template IDs only: no KQL, table, workspace, host, URL or path. Service names and operation IDs are
  validated and quoted as KQL string literals; operator template files are restricted to one approved table and
  forbid `union`, `join`, `let`, cross-resource functions, `externaldata`, `evaluate`, comments and `;`.
- Credentials and tokens are backend-only (`AZURE_`, `MSAL_`, `IDENTITY_` on the web-process denylist) and never in
  responses, logs, errors, snapshots or reports; credential errors keep only `AADSTS` codes.
- The isolated Playwright stack now starts Next.js through the same web-process allowlist as `make dev`, so the E2E
  API's backend credentials never reach the web process (D133).
- Least privilege: *Log Analytics Data Reader* on the one workspace.

## Compatibility

- No migration; snapshots use the existing columns (queries add `workspace` and `tables`).
- Loki/Prometheus prompt notes and report banners are unchanged; Datadog wording is unchanged. Every uploaded or
  connected report (Loki, Prometheus, Datadog, Azure, files) gains the *How to read this report* section, the
  snapshot-anchored impact line and the calibration notes (D135); their queries, evidence, prompts and empty-result
  wording are otherwise unchanged. Simulator reports are unchanged.
- API: `azure_monitor` joins the connector list and leaves `planned`; previews accept up to 4 sources;
  `ConnectionStatus` may be `permission_denied` and adds `tables`.

  snapshot holds errors from 10:31:33Z (capped log search, D134). The second run labels these as earliest returned.

  accessible records* badges.

## Known limitations

- **Not verified against a real Azure workspace**; synthetic fixture only.
- Native Azure Monitor resource metrics, sovereign clouds, classic (non-workspace) Application Insights and
  cross-workspace queries are not supported.
- Change history is not collected.
- `failed_requests` expands at most 10 operations within the record budget; sampling and missing correlation leave
  operations partial.
- Restricted (protected) tables answer with no rows when access is missing and the API does not distinguish that from
  no data: OpsPilot reports every empty Azure query as *No accessible matching records — access/coverage not
  independently verified* and does not look up permissions to resolve it.
- Claim calibration is deterministic pattern matching on English wording: it adds notes, it does not judge reasoning,
  and phrasings it does not recognize are not flagged.
- Role names with spaces, `:` or `/` cannot be queried; mixed-case roles are matched case-insensitively.
- Log Analytics queries may be billed per the workspace's plan; OpsPilot bounds how many it runs.
