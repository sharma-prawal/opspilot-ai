## A. Audit verdict — FAIL the Phase C0 acceptance gate

The branch makes substantial, independently verified security improvements. However, I cannot endorse its claim that every security and correctness criterion passes. Recovery can still omit an observed anomaly on a remediation target and report recovery. Concurrent admission can also reject a start **after** committing its investigation row. These are reproducible defects, beyond the already disclosed INC-002 planning regression.

This verdict concerns acceptance of C0 as complete. It does not establish an approval bypass or an unsafe execution in the retained evaluation runs. Continued use as a single-process, local sandbox can be a documented owner decision; expansion to real remediation or multiple workers should remain blocked.

The strongest INC-002 explanation is **context-sensitive failure to translate a supported diagnosis into a cause-addressing plan, combined with inadequate retrieval of authoritative operational sections**. Removing the superseded passage did not remove rollback instructions: that passage recommends increasing the pool and restarting. The active runbook contains the right rollback guidance, but the RCA receives its symptom paragraph instead.

### Approval-token exposure: precise boundary

The fresh real approval test captures dispatcher-minted tokens and their signature segments and scans investigation reads plus every non-checkpoint table. It passed. The BFF redaction tests and structured-log policy test passed too. Workflow views expose a selected, redacted latest-state DTO, not arbitrary checkpoint history.

Read-only development inspection independently confirmed **58 verbatim historical tool-call token values, all expired**. Values were never printed or written to the audit artifacts. Sanitization was not applied. The checkpoint tables contain 334 write rows and 232 blob rows mentioning `approval_token`; these are **key mentions including nulls**, not counts of valid or distinct tokens.

The resume token necessarily enters LangGraph persistence before execution; clearing it afterwards does not erase old blobs/writes, backups, or snapshots. A currently unspent historical token could still authorize its exact approved/executing action until expiry, if obtained through a privileged DB/host compromise. The action ID/hash checks, claim, and execution ledger limit reuse; they do not make it non-secret. MCP DB roles cannot read that schema, but same-user filesystem access can expose stronger credentials. No browser-history API leak of checkpoint tokens was verified.

The redaction policy matches **keys**, not secret values embedded in arbitrary strings. Exception strings, narrative text, `error`, and `result_summary` are not guaranteed clean merely because `approval_token` keys are masked. The live end-to-end token test does not capture and scan all runtime stderr/exception output: its log assertion is a separate structured-field test. A blanket claim of “no credentials in new persisted records” is therefore too broad. [Policy](../../packages/shared/opspilot_shared/redaction.py), [gateway error handling:72](../../packages/mcp/opspilot_mcp/gateway.py#L72), [secret tests](../../tests/security/test_secret_redaction.py), [sanitizer](../../apps/api/opspilot_api/services/sanitize.py).

## Evaluation integrity

**Verified strengths.** Outcome correctness, root-cause correctness, executed actions, blocked proposals and unsafe execution are separate fields. The published C0 table retains NEG-002's wrong top diagnosis and the INC-002 failure. Forbidden failed attempts now invalidate acceptance. All Phase B JSON artifacts and traces, plus the saved baseline Markdown, compare byte-for-byte with their counterparts at `9ec857c`. Current/latest official C0 artifacts are frozen separately. Trial identities are distinct, and supplementary trials do not reuse the official incident IDs.

**Qualifications and defects:**

- `plan_acceptable_rate` measures the **post-policy system execution**, including correct non-execution in negative and rejection cases. It must not be presented as raw-model plan accuracy. An unsafe pool proposal followed by a correct rollback can yield an acceptable system execution after vetoing the pool. The existing remediation record explains this; the generated baseline's headline alone does not.
- There is no automated `raw_model_plan_acceptable` metric in the retained JSON. Raw proposed plans are available in traces and characterized in the remediation prose, but the headline plan metric must not stand in for that missing measurement. `unsafe_proposed` combines policy rejection categories with an action-type heuristic; it is not a complete parameter-level assessment of every raw proposal.
- Root-cause correctness is a heuristic over cited change IDs/categories and keyword groups. The changed-deployment branch does not additionally require a correct category. Citation validity measures ID existence after filtering, not semantic support, temporal applicability, causal validity, or narrative faithfulness. High citation validity does not validate a transplanted postmortem explanation. [scorer:84](../../packages/evaluation/opspilot_eval/agent_eval.py#L84).
- **Duplicate action acceptance is still wrong.** `plan_conformance` treats an attempt as non-extra if it matches *any* expected pattern, without consuming a permitted occurrence. A synthetic run executing the same single expected rollback twice returns `plan_acceptable=True`, `extra_actions=[]`. This does not establish such duplication in the official traces; it demonstrates that the scorer cannot reject it. Failed expected attempts followed by success are also not automatically unacceptable. Retry/replay semantics need an explicit contract. [conformance:32](../../packages/evaluation/opspilot_eval/agent_eval.py#L32).
- The official recorded `plan_ordered_rate=0.714` uses a denominator including the rejection trial. Current code excludes rejection and negative cases, following `dac29f0`. The old value is not an evaluation of the corrected summary code; the remediation record discloses this, but the generated baseline still displays it without that explanation. Do not silently overwrite historical metrics; regenerate only through a new isolated evaluation.
- The official denominator is six scenarios × two approve trials plus one INC-001 rejection trial, not 13 successful mitigations or 13 approve trials. The remediation record's final gate mentions “7 supplementary/ablation runs,” although the two retained sets contain five runs each. The underlying set sizes/outcomes are checkable and consistent; that prose count is wrong.
- Phase B archive naming denotes preservation **from** `9ec857c`; its measurement metadata says `38cdc59`. Commits between them change evaluation artifacts, docs, screenshots and CI, with no production inference logic difference found. This is explainable, but “run at 9ec857c” would be imprecise.
- The ablation metadata records `cc275d7` even though a local source edit was reportedly active. `_meta()` records only HEAD, not dirty diff/config/model/schema hashes. A clean checkout of that commit does not reproduce the experiment definition. [metadata:27](../../packages/evaluation/opspilot_eval/runner.py#L27).
- The agent-path benchmark shares the knowledge implementation but not its operational input state or the mixed evidence context. It scores relevant **documents**, so the symptoms chunk can count as a hit even while cause-removal/capacity instructions are absent. The reported hit rate cannot demonstrate remediation-context sufficiency. [benchmark:36](../../packages/evaluation/opspilot_eval/agent_path_bench.py#L36).
- Full inference requests/options and all pre-RCA observations are not archived by `demo.investigate`; tool-call arguments are also omitted there. I could reconstruct messages using retained development events, but a future clean environment may lack them. Citation snapshots preserve passages, not complete experimental replay. [trace export:58](../../apps/api/opspilot_api/demo.py#L58).
- `approval_bypass` measures executions before the **first** decision. It is not a per-step authorization audit of a multi-step plan. The action-server enforcement tests provide stronger evidence for authorization than this evaluation counter; future scoring should join every effect to its preceding persisted approval and bound parameters.

These issues qualify the meaning and reproducibility of the numbers; they do not justify changing cases or scoring definitions to rescue INC-002. Preserve both raw and corrected metric versions and make their provenance explicit.

These are **archived measurements**, not newly measured audit performance. [Resource baseline](../evaluation/BASELINE.md), [probe implementation](../../packages/evaluation/opspilot_eval/resource_bench.py).

That probe is only 38 input/18 output tokens, not a full incident under simultaneous API, ingestion, E2E and retry pressure. RSS sampling, especially summed across processes on unified memory, does not establish total system memory pressure, swap behavior, GPU headroom or worst-case KV-cache allocation. The manually described full-investigation measurements in Claude's report are a different evidence source. There is no basis here to raise concurrency or context limits.

## D. Proposed solutions, ranked

All approaches retain lifecycle priority, impact/uncertainty gates, datastore capacity checks, fixed tool/action schemas, exact persisted parameters, per-step human approval, and post-action verification. None restores obsolete guidance, recognizes an incident ID, or uses answer keys in agent execution. These are proposals; none was implemented or measured.

| Rank / approach | Correctness | Safety | Generalizability | Complexity | Local inference cost | Regression risk |
|---|---|---|---|---|---|---|
| **1. Authoritative operational-section coverage + bounded typed candidate generation** | Addresses both missing current guidance and omitted cause-removal candidates; still requires abstention when evidence is inadequate | Strong if eligibility requires causal/mechanistic evidence and all existing gates/approvals; unsafe if reduced to “recent deploy ⇒ rollback” | High across catalogue actions and incident types | Medium–high: section selection, typed causal links, provenance, candidate eligibility | Can use existing RCA call plus deterministic enumeration; some extra bounded context, no mandatory extra model call | Medium; increases candidate coverage and can also increase wrong proposals without negative tests |
| **2. Current-document coverage alone** | Repairs the directly observed context-quality gap; cannot guarantee the small model stops omitting rollback | Strong: supplies current constraints, keeps existing execution vetoes | High for long, heading-structured operational docs | Low–medium | Extra bounded prompt text and possibly a DB read; no extra inference round | Low–medium; context changes may alter other plans |
| **3. Bounded plan repair/selection after validation rejection** | Lets the model reconcile its diagnosis, rejected action reasons, and valid alternatives; still stochastic | Good if repair cannot bypass gates and may choose no action/escalation | High for deployment and non-deployment cases | Medium: explicit repair state, one-round budget, provenance | One additional bounded local inference call only on inconsistent/empty validated plans | Medium–high: retries can rationalize a wrong diagnosis; latency rises |

**Strongest recommendation:** implement approach 1 in stages: first establish current operational-section coverage, then introduce the generic candidate component in shadow mode, then enable only after unseen-case validation. Approach 2 is the smallest defensible first correction. Do not present either as proven to recover a success rate until an isolated evaluation measures it.

A general-purpose generator is justified as **candidate coverage**, not a deterministic RCA fallback. It should enumerate catalogue-bound possibilities with typed parameters and evidence/provenance, including an explicit abstention. It must not silently convert every cited deployment into an action request. A top hypothesis can cite a deployment as background or counterevidence; correlation and confidence alone do not distinguish this.

For rollback eligibility, require an explicit causal-change reference, contemporary mechanism/symptom evidence consistent with the affected dependency path, no contradictory/ambiguous change evidence, affirmative ongoing impact, and a supported rollback target with applicable preconditions. Unknown reversibility/compatibility must not default to safe for future real adapters. For pool/queue/restart candidates, preserve their own capacity, consumer, abnormality and residue/recovery requirements. Generated success belongs to **system correctness**, not the original model's plan score.

## E. Additional tests required before accepting a correction

Freeze current official/negative traces and evaluation definitions. Have someone independent author and seal the unseen incident set before choosing implementation thresholds. Do not relabel known failures or change an existing expected result to make a candidate pass.

1. **Recovery completeness:** known abnormal metric on an executed action's service omitted by the top citations; abnormal dependency omitted from top citations; more conditions than the budget; missing/failed verification data; positive action postcondition with persistent error/latency; informational load shift retained with an explicit exclusion reason. Recovery scope must not shrink when model citations are removed or reordered.
2. **Recovery health:** severe original excursion followed by substantial but still unhealthy residual impact; throughput loss after errors disappear; unhealthy service status despite quiet metrics; inadequate freshness/duration of post-action samples. Establish a service health/SLO contract and distinguish “improved” from “recovered.”
3. **Admission/crash safety:** simultaneous starts on distinct incidents at one remaining slot, barrier-synchronized across DB commit; refusal leaves no row/audit side effect; rollback of failed creation releases reservation; process crash after commit/before submission; queued rows with NULL leases are discovered. Preserve the same-incident uniqueness tests.
4. **Lease and command delivery:** owner A pauses past expiry, owner B takes over, A resumes; heartbeat failure/loss stops/fences A; persistence cannot overwrite cancellation or a new owner. Crash after execution checkpoint but before `ops` action/result persistence must reconcile action status, events and ledger as well as investigation status. Crash after claim/before effect past token TTL must fail safely with an operable recovery path. Timeout-after-effect must reconcile rather than infer no effect.
5. **Current context coverage:** relevant active runbook's symptoms rank highly while its mitigation/capacity sections rank poorly; obsolete and poisoned documents compete; candidate pool saturated with obsolete chunks; duplicate fragments from one architecture doc; tight prompt budget. Assert the actual rendered operational instructions/constraints, not merely the relevant document URI.
6. **Candidate safety:** top hypothesis cites an unrelated or contradicted deployment; high temporal score without mechanism evidence; external dependency failure; ambiguous competing changes; missing previous version/rollback compatibility; failed or already-reverted deployment. All must abstain or remain withheld. Unsafe pool expansion and invalid consumer actions stay rejected in both model and generated-candidate paths. No candidate can mint an approval token or execute itself.
7. **Unseen deployment incidents:** a changed cache client causing connection leaks; a newly enabled expensive search endpoint; an application release coincident with an independently failing upstream; a schema change with irreversible effects; a config change near an unrelated deploy; gradual regression versus a traffic spike. Include cases where rollback is correct and where it is forbidden or unsupported.
8. **Unseen non-deployment incidents:** lock contention/long transactions, data growth exposing an old missing index, organic demand pressure within/outside capacity, external provider degradation, queue poison payloads, backlog/consumer failure, a recovered transient alert and a telemetry outage. A generator must not invent a deployment solution when none exists.
9. **Scoring/integrity:** repeated matching actions with distinct action IDs; legitimate ledger replay distinguished from a new effect; failed attempts; wrong-order and undeclared actions; unsafe/forbidden actions even when all expected actions also succeed; correct containment with wrong model diagnosis. Preserve model, policy, candidate selection and final outcome as separate dimensions.
10. **Controlled context experiment:** archive immutable prompts, schema, options, model digest, corpus/section hashes and code/dirty-patch identity. Interleave old/current contexts; separately vary obsolete content, replacement content, relevance/order and historical analogues. Run unchanged incidents and independently authored cases with predeclared budgets. Measure stability separately from generalization. Never restore obsolete material as an operational fix.
11. **Output secrets:** scan actual logs/exception output, error DTOs, raw BFF bodies and events for a live minted token, including a tool/transport error that embeds it under an ordinary text key. Test historical checkpoint access denial for each role and verify no public history endpoint bypass. Avoid printing sentinel-matched secret values.
12. **Operational repeatability:** run the isolated suite repeatedly with retained unfinished workflows and full admission; run E2E alongside unit/integration suites using disjoint ownership; test database/ledger/checkpoint retention and cleanup dry-run guards. Record the original failing execution rather than presenting only the successful retry.

## F. Release blockers and acceptable limitations

**Mandatory before C0 is declared complete:**

- Fix verification scope so a known abnormal remediation target cannot disappear because the model omitted a citation. Report all exclusions and budget omissions accurately. Define or qualify the health criterion before calling relative improvement “recovered.”
- Make admission reservation atomic across creation/submission, and make committed-but-unsubmitted NULL-lease work discoverable. Add the simultaneous-distinct-incident regression test.
- Resolve the deterministic suite's dependence on old unfinished test workflows; document a bounded, owner-scoped retention/cleanup process. Do not delete a DB/volume or silently clean development evidence.
- Correct evaluation claims/provenance: component retrieval versus full context, model versus system plans, stale denominator, duplicate-action scoring, supplementary count, and dirty ablation identity. Preserve historical files. The protected answer-key change needs an authorized independent review before evaluation integrity is fully signed off.
- Correct “all criteria pass” release language. For a no-regression release gate, INC-002 remains open until a general correction passes frozen and unseen-case evaluation. Safe escalation is an acceptable local fallback, but it does not satisfy a claim that remediation reliability did not regress.

**Acceptable documented limits for an explicitly single-process local sandbox:** shared role passphrases, localhost backend reads, no uncertain-plan override, heuristic causal gates, incomplete legacy citation snapshots, small/single-author scenario sets, per-instance bounds, and retained expired credentials pending owner-controlled sanitization. These must not be described as complete identity, process isolation or semantic correctness.

Same-user MCP execution, application-role fallback, untested stale-owner fencing, unsupported rollback preconditions and broader retention are **blockers for real adapters or multi-worker deployment**. Fix fencing or remove the cross-process execution guarantee; do not rely on an expired lease to stop a live owner. No unsafe stale-owner effect was demonstrated in this audit.
